# Engineering quality and acquisition readiness

Accepted build requirement, 17 November 2026: Debrio's programming structure and quality must support serious technical due diligence by a potential acquirer such as Google, Meta or an LMS company. This is a requirement from the start of implementation, not a cleanup phase after the product works.

The [PRD](../Debrio_PRD_v0.5.md) remains the product source of truth. This contract defines the engineering evidence required to support that requirement. These are Debrio's acceptance gates, not a claim to know or satisfy any company's private acquisition criteria. Commercial acquisition, legal clearance and buyer approval are separate outcomes.

## Required gates and ownership

| Gate | Required outcome and evidence | Delivery owners |
|---|---|---|
| QG-01: understandable architecture | Keep the accepted modular application. Document module responsibilities, dependency direction, data ownership and trust boundaries in ARCHITECTURE.md and consequential decisions in ADRs. Separate workshop rules from UI and provider SDK details through the smallest useful boundaries. Review for cycles, duplicated rules and cross-module data access that bypasses the owning module's policy. Exercise important boundaries in tests; do not add speculative services or generic provider frameworks. | P0-02 establishes; every feature preserves; P7-02 reviews |
| QG-02: reproducible, enforced checks | A clean checkout with documented non-secret configuration installs from a lockfile, provisions a disposable test database, applies migrations, checks formatting/lint and strict TypeScript types, runs relevant automated tests and produces a production build. CI runs on PRs; configure required checks and review protection for the default branch. Demonstrate that a deliberate failure blocks delivery, then remove it. Record actual commands, tool versions and CI results for the exact revision. | P0-01 repository protection; P0-03 implementation; every feature maintains |
| QG-03: behavioral correctness | Trace requirements to executable proof. Test domain boundaries, real database permissions and migrations, concurrency, duplicate/reordered events, retries, interrupted writes and critical browser journeys. Include billing/entitlement, tenant isolation and access revocation negatives. Mock tests alone cannot certify provider behavior or database policy. Do not substitute a coverage percentage for scenario evidence. | Every implementation task; P5-01 integrated verification |
| QG-04: security and privacy | Maintain a threat model covering identity, privileged operations, workspace/session/audience boundaries, public endpoints, uploads and provider callbacks. Enforce authorization on the server/database, scoped credentials, input validation and safe logs. Automate secret, dependency and supported static security checks. Verify retention/deletion and recording-disabled behavior. Review findings and fixes against the release candidate; retain evidence without customer data or secrets. | P0-02 threat model; P0-03 checks; P2-01/P4-05/P6-03 implementation; P5-01/P7-02 verification |
| QG-05: recoverable operation at stated capacity | Prove the existing PRD targets and R1-R8 reliability scenarios at the published limits. Record measured latency, endurance, capacity and provider usage; exercise alerting, backup restoration, compatible migrations and deployment rollback/recovery. Document measured recovery time and data-loss window against accepted objectives, incident ownership and support procedures. Restore must not resurrect revoked access or deleted content. | P5-02 operations; P7-01 capacity; P7-02 candidate evidence |
| QG-06: usable and accessible product | Critical journeys pass keyboard/focus, screen-reader and supported-browser/device checks, including failure and reconnect states. Carry the PRD's accessibility and media criteria through implementation. Automated accessibility checks supplement manual proof. Record limitations explicitly. | Every UI task; P1-06 media; P5-01/P5-03 integrated and pilot proof |
| QG-07: dependency and asset provenance | Keep a versioned dependency inventory/SBOM for the release candidate, dependency/license findings and an inventory of third-party code, fonts, media and other shipped assets with source and usage rights. Record contributor ownership/assignment evidence where applicable; identify unresolved provenance instead of assuming downloaded or generated assets are cleared. Document provider dependencies, account control and data export/exit constraints. | P0-01 baseline inventory; P0-03 dependency tooling; every addition; P7-02 final inventory |
| QG-08: transferable implementation | A reviewer other than the implementer can follow the docs to build, test, operate staging and perform the documented restore/export procedure without undocumented author knowledge. Link architecture/ADRs, schema/migrations, API/event contracts, configuration names, runbooks, evidence, asset inventory and owned/time-bounded technical debt from the release record. Exercise the handover and record gaps; never put credentials in it. | P0-02 contracts; P5-02 runbooks; P7-02 independent handover |

## Applying the gates

- Every task records applicable QG IDs, Pass / Fail / Unverified results, exact source revision, evidence location and remaining gaps. N/A requires a reason. Foundation tasks establish controls; feature tasks extend them without deferring correctness, security or maintainability to release.
- P0-03 adds real automated commands to COMMANDS.md. CI must reject failed required checks; a local hook is not enforcement. Unavailable branch protection or scanning capabilities remain an explicit gap until an effective control is verified.
- P7-02 assembles one evidence index in its existing task/release record. Evidence must apply to the candidate revision and service configuration; rerun affected checks after fixes. An independent code review is required, with reviewer, scope and limitations recorded. An AI review is not an independent professional security assessment or buyer sign-off.
- Release is blocked by failed required gates, unresolved critical/high security findings, known unauthorized disclosure, acknowledged-data loss, incorrect billing, or unresolved rights to shipped material. Lower-risk debt needs severity, impact, an owner and a remediation date. An unavailable required check is Unverified, never Pass; do not silently waive it.
- The no-additional-infrastructure-spending constraint remains. Prefer existing/platform tooling. If a required control cannot be provided within available allowances, record the specific blocker and obtain a scope/budget decision; do not lower the quality claim or purchase services implicitly.
- Buyer-specific diligence, paid certification, external penetration testing and new LMS integrations require their own scope when requested or required by a buyer. This requirement does not add SCORM, LTI, xAPI or a service fleet to the initial product.

## Current evidence status

The repository currently contains planning documents, local skills and a reference mockup. There is no application build/test command registry or verified CI pipeline. QG-01 through QG-08 are **Unverified**. Recording this contract does not certify the product or complete any implementation task.
